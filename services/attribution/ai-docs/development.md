## 1. 本轮范围和实际进度

已建立可安装的 `ear-attribution` 包，并加入 uv workspace、pytest 与 pyright 的检查范围。

已实现 `AttributionService` 的事件处理框架：

- 只依赖 `StorageClient`，生产代码不依赖 `MemoryStorage`。
- 对新增声纹、GPS、用户反馈及以归属关系为目标的重新判断请求进行路由；无关事件忽略。
- 在快照中读取目标的当前版本；不能只凭事件里的旧版本作业务判断。
- 业务策略通过 `Planner` 注入。策略返回操作序列，框架把它与 `MarkProcessed` 原子提交；乐观锁等可重试冲突会重新读取和计算。
- 业务策略返回 `None` 表示事件不归自己处理；返回空序列表示已处理但无内容变化，框架只写去重标记。重复事件不重复执行已提交的策略。
- 已整体替代的归属关系不重新判断；目标丢失或类型错误会抛异常，让总线处理重试/死信。
- 执行反馈时使用反馈本身的 id、深度 0；执行重新判断时原样传递请求的根源反馈与深度。
- 输出包含 `module`、`event_id`、`root_feedback_id`、`depth` 的 JSON 日志。

**尚未实现**：声纹/GPS 匹配、新建未命名人物、未知地点初始化、参考管理、纠正确认、改名、新建地点、按时间范围重新归属、空未命名人物清理、候选依赖登记、⑤的完成回报、⑦接入。框架没有默认业务策略，不会把未完成能力伪装成成功处理。

## 5. 内部实现选择与下一步

框架采用同步 `StorageClient`、只读计划器、原子提交与乐观重试。这些是模块内部组织方式，不添加公共契约。计划器可能因冲突重复调用，必须不直接写库、不调用外部动作；大模型调用若有需要仍必须经过⑦，不能藏在可重复计划器中随意调用。

接口确认后分批实现：

1. P1/P2/P4 确认后：待归属扫描、声纹与地点匹配、新建未命名人物、未知地点兜底；匹配阈值由③负责人选择，必须显式配置。
2. P3/P5 确认后：反馈模型、纠正确认与参考管理、用户保护、地点创建与命名、按范围重新归属。
3. P6 确认后：候选依赖、重新判断不变时更新依赖、结果回报、改名不触发重判、空未命名人物清理。
4. P7 就绪后：真实输入、持久化、部署与端到端联调。
