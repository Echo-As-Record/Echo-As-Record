# Ear MVP 工作分解 v1.1（分工会议用）

> 定稿日期：2026-10-26
> 配套文档：《Ear 设计文档 v1.1》。本文中的节号指设计文档的节号。
> 本文列出 MVP 的全部工作部分。每一部分包括：说明、工作内容、依赖、交出、验收标准、由负责人决定的内容和工作特点。
> 分工在会上决定。模块内部怎么实现由负责人决定，本文只规定模块边界、交接内容和验收标准。
> 只列【MVP】工作；标为【预留】的约定在实现时必须遵守；【以后】的功能不在本学期工作范围内。

---

## 0. 所有部分共同遵守的约定

1. **原始数据只追加，不修改。** 语义信息（人物、地点、归属关系、活动、md 产物、外部动作建议、规则）的 id 永远不变，每次修改记一个新版本，旧版本标记为"已被替代"并保留。
2. **每类数据只有一个模块负责写：**

   | 模块 | 负责写的数据 |
   |---|---|
   | ② 适配器 | 外部来源的原始数据 |
   | ③ 归属模块 | 人物、地点、归属关系、参考 |
   | ④ 活动提取模块 | 活动、md 产物、外部动作建议、规则 |
   | ⑤ 依赖分析模块 | 传播记录 |
   | ⑥ 客户端与 API | 用户反馈 |

3. **用户的所有操作一律先存为用户反馈**（一种原始数据），再由负责那类数据的模块执行。手动提取、审核建议、外部动作的执行结果也都是这样处理。
4. **统一输入格式**：每条原始数据都要有 id、类型、事件时间区间、入库时间、来源、适配器版本、去重键，以及具体数据（大文件只存引用）。
5. **总线上只有两种事件**，字段只能加不能少（设计文档第 4 节）：
   - 「数据库被修改」：数据类别、数据 id、操作（新增 / 修改 / 标记为已被替代）、新版本号、旧版本号、根源反馈 id、依赖分析深度、是否处理历史。
   - 「请求重新判断」：目标类别、目标 id、起因（类别、id、新旧版本）、可读的修改描述、根源反馈 id、依赖分析深度。
6. **根源反馈 id**：由用户操作引起的修改，带上那条用户反馈的 id；系统发起的行为（如定时提取）标为"系统"。
7. **md 产物和活动的名称、描述用 Markdown 书写**，人物和地点一律写成引用标记 `[[person:<id>]]`、`[[place:<id>]]`，由 ⑥ 在显示时换成当前的名字。
8. **外部动作只有两种**：写入日历（标题、开始时间、结束时间、备注）；写入提醒事项（标题、截止时间、备注）。
9. **调用大模型一律经过 ⑦**，并带上调用方模块和根源反馈 id。读写数据库、调用大模型都直接调用，不经过总线。
10. **【预留】扩展性约定**（设计文档第 10 节）：核心数据不能依赖以后的扩展数据；① 的读取接口和事件格式按对外公开的约定来写和维护；⑤ 按登记表分发请求，不在代码里写死接收方。以后的检索索引模块（⑧）也按这套方式接入。

## 2. 各工作部分

### ① 存储与事件

**说明**：所有模块都通过它读写数据、收发事件。"去重""版本""内容没变就不写""写入后自动发事件"这些规则只在这里实现一次。

**工作内容**
- 部署数据库和总线。
- 统一的写入接口：
  - 原始数据按去重键去重；
  - 语义信息写入时生成新版本，旧版本标记为"已被替代"；
  - 内容没有变化时不写入；
  - 写入成功后自动发出「数据库被修改」。
- 读取接口：按 id 读当前版本；按 id 和版本号读任意历史版本；按时间范围和类型查原始数据。
- 依赖的登记和查询接口：查出"依赖了某个对象、并且登记的版本已经过时"的所有记录。
- 提供基础设施，保证同一个事件被送达多次时，各模块能做到结果和只送达一次相同。
- **最先交付**：接口说明和一个能用的初版，供其他部分对接。
- 【预留】接口说明按对外公开的约定来写，以后的扩展可以直接使用。

**依赖**：无。
**交出**：读写接口、依赖接口、「数据库被修改」事件、接口说明文档。

**验收标准**
- 同一条原始数据写入多次，只存一条。
- 写入成功就一定发出事件，写入失败就一定不发。
- 内容没有变化时，不产生新版本，也不发事件。
- 能读出任意对象的任意历史版本。
- 依赖查询不遗漏。

**由负责人决定**：数据库和总线的选型、表结构、事务和事件可靠投递的实现方式。
**工作特点**：后端和数据库经验；会卡住所有人，需要最早开始、最早交付接口说明。

### ② 适配器

**说明**：把各种外部数据统一成一种格式，后面的模块不用关心数据从哪里来。只做确定的计算，不做任何推断。

**工作内容**
- 扫描服务：发现 Octopus 目录中的新文件，并确认文件已经写完。
- 声音适配器：封装现有的 Ear 基础处理模块（保留，不重写），输出录音引用、转写段、局部说话人、声纹、环境声。
- GPS 适配器：每个 GPS 点存为一条原始数据，采样间隔由负责人决定。
- 手机信息适配器：电量、屏幕、前台应用、Wi-Fi 等。
- 为每条数据填好统一输入格式的字段，尤其是时间区间、来源（含"来自哪个用户"）、适配器版本和去重键。

**依赖**：① 的写入接口。
**交出**：入库的原始数据；每类数据具体内容的字段说明，供 ③、④ 使用。

**验收标准**
- 用真实数据（天数待定）跑一遍，所有文件都能入库，不重复，不遗漏。
- 扫描服务重启后重新扫描，不会产生重复数据。
- 时间区间和真实时间对得上（允许的误差待定）。

**由负责人决定**：扫描方式、时间对齐的方法、Ear 的调用和封装方式、GPS 采样间隔。
**工作特点**：规则确定，边界清楚。Ear 封装需要熟悉 Ear 的人参与。

### ③ 归属模块

**说明**：认人、认地点。它有自己的规则（参考、未命名人物、未知地点），和活动提取的触发时机不同。

**工作内容**
- 新的声纹、GPS 点入库后，为它们建立归属关系：
  - 已经是某个对象参考的数据，直接归属到这个对象；
  - 认不出的声纹：新建未命名人物，用这条声纹作为它的第一个参考；
  - 认不出的 GPS 点：归属到全局唯一的"未知地点"。
- 执行归它处理的用户反馈：纠正、确认、增减参考、新建地点、命名或改名、按时间范围重新归属。
  - 纠正或确认时，这条数据成为目标对象的参考，同时从原对象的参考中移除。
- 某个人物的参考全部被移走后，这个人物保留，但不再参与匹配。名下已经没有声纹时，把它标记为"已被替代"。为 ⑥ 提供"#N 还有 M 段声音，可能也是 X"这类提示所需的数据。
- 登记归属关系的依赖。目标是：某个对象的参考改了以后，⑤ 能找到受影响的归属关系。
- 收到「请求重新判断」后，重新归属指定的那条数据。

**依赖**：① 的接口；② 产生的声纹和 GPS 数据（开发初期可以先用假数据）；可能用到 ⑦。
**交出**：人物、地点、归属关系、参考及其版本；依赖登记。

**验收标准**
- 提取前需要归属的数据，都有归属对象。
- 用户纠正或确认过的数据，任何重新归属都不会改变它的归属结果。
- 一条数据最多只作为一个对象的参考。
- 改名不会引起任何重新归属。
- 用户修改参考并选择重新判断后，以前曾把这个对象当作主要候选的归属关系都能被找出来。
- 在 D2 的标注数据上，认人准确率达到标准（指标待定）。

**由负责人决定**：匹配算法、阈值、依赖里登记哪些候选、未命名人物的处理细节。
**工作特点**：有一定的算法量。可以先用最简单的"找最像的声纹"跑通，再逐步改进。

### ④ 活动提取模块

**说明**：把一段时间变成活动、md 产物和外部动作建议。这是产品产出价值的地方，也是工作量最大的部分。

**工作内容**
- 定时提取（定时器在本模块内部）：范围是从上一次成功的定时提取结束的时刻，一直到现在，并去掉已经成功提取过的时间段。
- 执行归它处理的用户反馈：
  - 手动提取或重新提取某段时间；
  - 规则的新增、修改、删除；
  - 只改这一次的提取（作为一条只适用于某个活动的规则存储，并立即提取）；
  - 把规则应用到历史活动（结果追加到这个活动）；
  - 审核外部动作建议；
  - 外部动作的执行结果。
- 前置检查：这段时间里需要归属的数据都已经有归属对象。没有就延后重试，超过等待上限就放弃，并给出提示。
- 划分活动、选择适用的规则、按规则提取，md 产物按约定格式书写。
- 登记 md 产物的依赖：所属活动、规则版本、活动时间范围内的所有归属关系。
- 规则带有动作时，生成外部动作建议，并记下它来自哪条 md 产物的哪个版本。md 产物出了新版本时，把旧版本上还没审核的建议标记为"已被替代"，再重新生成。
- 重新提取时，这段时间里的旧活动和旧 md 产物全部标记为"已被替代"。执行前给出提示数据："有 N 个活动带有你的修改"。
- 收到「请求重新判断」后，用同一条规则，带上旧版本和修改原因，重新提取指定的 md 产物。

**依赖**：① 的接口；③ 的归属关系（初期可以用假数据）；⑦。
**交出**：活动、md 产物、外部动作建议、规则及其版本；依赖登记。

**验收标准**
- 能处理一整天的真实数据，中间不失败。
- 活动边界和 D2 的标注大致一致（指标待定）。
- 用 D3 的规则测试集：应该触发的规则会触发，不该触发的不会触发。
- 定时提取不漏时间段，也不覆盖已经成功提取过的时间段。
- **修改没有影响到的 md 产物，重新判断后的输出和旧版本完全相同。**

**由负责人决定**：提示词、长数据的切分方式、划分活动的方法、规则选择的方法。
**工作特点**：工作量最大，大模型应用开发；需要较多、较连续的时间。

### ⑤ 依赖分析模块

**说明**：项目的核心创新。修改怎样传播、为什么会停、每一步由什么引起，都集中在这里实现和记录，也是论文实验的数据来源。

**工作内容**
- 监听「数据库被修改」，只处理"已有的语义信息被修改"的事件。事件标记了"不处理历史"时跳过。
- 通过 ① 查出受影响的归属关系和 md 产物。
- 查出修改前后的两个版本，生成可读的修改描述，比如"局部说话人 C：丙 → 丁"。
- 按"**数据类型 → 负责模块**"的登记表分发「请求重新判断」。MVP 登记表里只有：归属关系 → ③，md 产物 → ④。不在代码里写死接收方，以后扩展可以登记进来。
- 保证传播会停；避免同一条记录被重复请求重新判断。
- 记录完整的传播过程：根源反馈、每一步的起因和目标、结果有没有变化、在哪里停下。
- 准备论文实验需要的统计和导出（结合 ⑦ 的调用记录）。

**依赖**：① 的依赖查询；③、④ 能处理「请求重新判断」；⑦ 的调用记录。
**交出**：「请求重新判断」事件；登记表；传播记录。

**验收标准**
- 用 D1 的模拟组会和收集到的冲突场景构造测试：受影响的信息一条不漏。
- 任何一次修改引起的传播，都在有限步内停下。
- 每一次修改都能追溯到最初的那次用户操作。
- 在登记表里新增一种数据类型和负责模块，不需要修改 ⑤ 的代码。
- 端到端流程第 6、8 步通过（见 I）。

**由负责人决定**：深度上限、去重方式、传播记录的格式、登记表的形式。
**工作特点**：研究性强，和论文关系最紧密；需要和 ①、③、④ 密切对接。

### ⑥ 客户端与 API

**说明**：用户只通过它和系统交互。它不做任何推断，只负责展示、收集用户反馈，并执行外部动作。

**工作内容**
- 服务端 API：读取时间线、活动、md 产物、人物、地点、规则、外部动作建议；写入用户反馈。只用一个访问令牌鉴权。
- 客户端界面：
  - 时间线、活动详情、md 产物显示（把引用标记换成当前的名字）；
  - 纠正和确认归属关系，以及纠正后显示的"同时重新判断其他相关记录"按钮；
  - 人物和地点页面：管理参考、命名，修改参考时询问是否重新判断以前的数据；
  - "#N 还有 M 段声音，可能也是 X"这类提示；
  - 新建地点：在时间线或地图上选中一些 GPS 点；
  - 规则管理、只改这一次的提取、把规则应用到历史活动；
  - 手动提取和重新提取（显示"有 N 个活动带有你的修改"的提示）；
  - 按时间范围重新归属；
  - 审核外部动作建议；
  - 用户操作提交后，显示"处理中"状态。
- 用户反馈适配器：把界面操作转成结构化的用户反馈。各类反馈的格式要和 ③、④ 约定好。
- 审核通过后，把建议写入手机的日历或提醒事项，并把执行结果作为一条反馈写回。

**依赖**：① 的读取接口（初期可以用模拟接口）；③、④ 对用户反馈格式的约定。
**交出**：用户反馈；外部动作的执行；用户反馈格式说明（和 ③、④ 共同维护）。

**验收标准**
- 设计文档第 11 节"用户可以做的修改"清单，每一项都有界面入口，并能正确写入用户反馈。
- 审核通过的建议能写进手机的日历或提醒事项。
- 端到端流程第 4、5、7 步通过。

**由负责人决定**：技术栈、界面设计、是否推送、"处理中"状态怎么显示。
**工作特点**：工作量大，前端或移动端开发；相对独立，适合异地开发。

### ⑦ 大模型入口

**说明**：所有大模型调用的统一入口，基于 Octopus 现有的大模型接入部分改成独立服务。它让用量、报销和传播记录能互相对上。

**工作内容**
- 把大模型接入独立成一个 docker 服务，后端对接反代平台。
- 换模型、限流、重试都在这里统一处理。
- 每次调用都留下记录：调用方模块、根源反馈 id（系统发起的调用标为"系统"）、用途、用量、耗时。
- 提供用量统计：按模块、按根源反馈分别统计。

**依赖**：无。
**交出**：调用接口、调用记录、用量统计。

**验收标准**
- 没有带调用方模块的调用会被拒绝。
- 用量可以按模块、按根源反馈统计。
- 能把 ⑤ 的一条传播记录和它引起的所有大模型调用关联起来。

**由负责人决定**：实现方式、日志格式、限流策略。
**工作特点**：工作量小，有现成基础，适合尽早完成。

### D1 模拟组会

**工作内容**
- 编写脚本：几位组员各说几段，其中有一条明确的待办，地点固定在实验室。脚本中要设计至少一个需要用户纠正的认人场景，用于端到端流程第 5、6 步。
- 按脚本录制，同时采集 GPS。
- 整理标准答案：谁在什么时候说话、活动边界、应该提取出的待办、应该生成的建议、纠正后应该变成什么。

**交出**：录音和 GPS 数据、标准答案文档。
**验收标准**：数据能被 ② 正常入库；标准答案足以判断端到端流程中的每一步是否正确。
**工作特点**：工作量小，需要几位组员同时参与录制；可以结合收集到的冲突场景来写。

### D2 标注数据

**工作内容**
- 选取一部分真实数据（数量待定），标注每段声音是谁、活动的起止时间和类型。
- 只使用录音提供者同意使用的数据。

**交出**：标注文件，以及标注格式说明。
**验收标准**：标注格式能直接用于计算 ③ 的认人准确率和 ④ 的活动边界一致度。
**工作特点**：工作量中等、耗时；最好由录音提供者本人标注，因为他认识录音里的人。

---

### D3 规则测试集

**工作内容**
- 编写一组提取规则，覆盖常见场景（组会、上课、闲聊等），其中包括带条件的规则和带外部动作的规则。
- 为每条规则准备应该触发和不应该触发的活动例子。

**交出**：规则测试集。
**验收标准**：能直接用于 ④ 的规则选择测试。
**工作特点**：工作量小，不需要写代码，碎片时间也能完成。

---

### I 集成与端到端验收

**工作内容**
- 编写 docker compose，做到一人一套、一键部署。
- 维护公共约定（第 0 节）和设计文档，处理各部分之间的接口问题。
- 组织联调，跑通端到端流程（使用 D1 的数据）：
  1. 组会录音和 GPS 入库（②）
  2. 声纹归属到人物，GPS 点归属到地点（③）
  3. 定时提取：划分出组会活动，生成笔记、待办等 md 产物和"写入提醒事项"的建议（④）
  4. 在 App 里看到时间线和 md 产物（⑥）
  5. 纠正"A 不是甲，是乙"（⑥ → ③）
  6. 待办负责人改为乙；未审核的建议重新生成；和这次纠正无关的 md 产物保持不变（③④⑤）
  7. 审核通过建议，手机提醒事项里出现正确的内容（⑥ → ④）
  8. 能查出这次纠正引起的完整传播记录，以及过程中的每次大模型调用（⑤⑦）
- 用真实数据连续跑一整天，检查中间不会失败。
- 作为回归测试固定下来，学期末演示也使用这套流程。

**验收标准**：8 步全部通过；真实数据能连续跑完一整天。
**工作特点**：持续性工作，需要对全局最熟悉的人；建议由组长或 ① 的负责人兼任。

---

## 3. 先后顺序与并行方式

```
第一步   ① 交付接口说明和初版；⑦ 独立成服务；
         D1 编写脚本并录制；D3 开始编写
            │
第二步   ②、③、④、⑥ 并行开发（先用假数据或模拟接口）；D2 开始标注
            │
第三步   ③、④ 支持「请求重新判断」；⑤ 开始联调
            │
第四步   I：端到端联调，跑通 8 步流程
```

- ① 的接口说明、事件格式、md 产物格式、用户反馈格式越早定下来，其他部分越能并行开发。
- ③、④、⑥ 开发初期都可以不等上游，先用手工构造的假数据开发和测试。

## 4. 不在本学期工作范围内

设计文档第 13 节列出的【以后】功能都不在本学期范围内，包括：检索索引模块（⑧）、问答与按需补充、会形成环的依赖分析、多用户支持、隐私控制、合并人物、直接修改活动或 md 产物、自动触发提取、细粒度依赖、新的外部动作类型、更多输入渠道、具体的扩展。

实现时请遵守【预留】约定（第 0 节第 10 条），不要把这些功能的路堵死。

5. D2 标注哪些数据、标注多少。
