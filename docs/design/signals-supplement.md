# 模块间信号（设计 v1.2 补充）

> 本文与[设计 v1.2](design-v1.2.md)共同描述当前目标，依据负责人本轮明确确认与同步授权更新。保留的 reviewed 字段仅为历史审核记录，不代表本轮正文已经重新人工审核。旧时序已由本文流程替换。
> [动态插件 MVP](plugins-mvp.md)统一定义插件生命周期与权限；[存储与运行模块 ADR](../adr/0001-storage-and-runtime-modules.md)定义架构选择；[决策索引](../decisions/mvp-confirmed-decisions.md)记录采纳来源。本文不声明新接口、类型或枚举已经实现。

## 1. 两类通信与两种事件

| 通信 | 用途 | 边界 |
|---|---|---|
| 直接调用 | 经① SDK 读写、查询依赖/完成记录；经⑦调用模型 | 计算在存储事务外，批次校验与提交在①内 |
| 总线事件 | 数据库被修改、请求重新判断 | 不新增管理完成或重判完成的第三类事件 |

一般业务模块只向①写自己的数据，由①产生变更事件，不直接向其他业务模块下指令。⑤是请求重判的唯一发出方；①的管理处理器消费自身管理反馈后调用内部逻辑，不经 HTTP 自调，不接管③④⑤业务。

| 事件 | 唯一发出方 | 触发 | 接收与分发 |
|---|---|---|---|
| 数据库被修改（`data_changed`） | ① | 原始/业务数据、归属、规则等写入或整体替代；系统记录不触发 | 按获批类型与订阅范围投递给①管理处理器、③④⑤⑥及插件；未来⑧同样按授权接入 |
| 请求重新判断 | ⑤ | 当前有效目标存在过时依赖且满足门控/上游就绪条件 | 按登记类型的所属模块及是否支持重判分发给③④或插件 |

②由文件扫描等输入驱动，通常不消费这两类事件；⑦通过直接调用工作。①**消费其管理反馈事件**。动态登记不只在启动时读取，①⑤须支持运行中发现；不另设独立于 owner 的第二重判执行人字段。

## 2. 通用处理规则

### 2.1 授权、当前状态与幂等

- 事件按授权范围过滤投递，订阅独立获批且不得超过读取范围；不是所有消费者先收到全量数据再自行过滤。
- 获准事件到达后仍须查询当前状态，确认对象有效、请求未完成且职责相关；重复、过期或不相关事件不能直接驱动重复写入。
- 事件只含对象/版本/因果上下文和必要变化说明，不带业务正文。当前、历史、按 id、query、依赖等读取均由①检查权限；不能只在界面隐藏。
- 至少一次投递必须结合消费标记、稳定请求身份、并发保护和批次提交实现内部幂等，不能仅凭一次查状态保证所有重复场景。
- 写成功的业务变化经 Outbox/Relay 可靠最终投递；写失败不产生对应事件。数据库与总线不是跨系统单事务，重投、死信和恢复须可观察。
- 无变化不新增业务版本、不发业务变更事件，但仍提交完整依赖和重判结果，不能把“无事件”解释为“没完成”。

### 2.2 根源、深度与多起因

直接执行反馈产生的写入使用该反馈 id，深度为 0；系统行为使用 `system`。⑤从事件发请求时沿因果路径增加深度；直接执行“重新判断其他相关记录”反馈时触发深度按 0 计。执行模块沿用请求上下文，不自行重置根源。

同一目标的多个原因尽量合并，但保留全部起因对象、版本及其根源；执行时发现当前规则变化/删除也追加起因。多 cause、跨 root 合并以及既有单 cause、`root_feedback_id`、`depth` 的兼容表达待契约设计，不用一个新造字段或随便选择单一 root 掩盖其他来源。

模型调用携带调用方、根源和重判请求 id。传播记录与所有相关调用可关联；多起因下的关联格式同样待契约同步。

### 2.3 历史门控与规则例外

| 变化/操作 | 处理方式 |
|---|---|
| 纠正/确认时伴随的参考修改 | 默认不重新判断其他历史归属；纠正后按钮可显式发起 |
| 单独增减参考、用户选择不重判历史 | 对该参考变化设置不处理历史门控 |
| 单独增减参考、用户明确选择重判 | 放行相关过时依赖 |
| 归属关系本身改变 | 可传播给依赖它的产物、选规则结果及获授权插件；不重划活动 |
| 首次命名/改名 | 触发 name 字段依赖者；只依赖参考字段的归属不受影响 |
| 规则新增、修改、删除 | 编辑本身不主动重算历史；其他输入引发重判时再按当前规则处理 |
| 上游整体替代 | 依赖过时，下游由所属方重判；①不级联删除，已确认归属仍受保护 |
| 明确重新提取时间段 | 替代旧活动/产物并生成新活动；已有插件下游仍需处理 |
| 插件历史范围补处理 | 必须单独获得用户明确选择，读历史上下文不构成此授权 |

“不处理历史”用于特定变化的门控，不把一次参考修改的门控扩散到同批归属变化，也不能把规则编辑例外误解为后来重判仍用旧规则。整体替代后的依赖失效不能被当作“字段没变”；无有效结果须明确不可用或替代，不能默认成功。

### 2.4 版本事件与依赖检查

版本语义遵循[主设计 R6](design-v1.2.md#32-不可变版本模型r6mvp)：普通修改追加版本，历史 status 不变；整体替代追加内容同旧版的终止 `superseded` 版本，事件 `old_version=n`、`new_version=n+1`。重复替代不再写版本/发事件；终止后拒绝后续修改。

依赖省略 fields 按全对象版本；指定 fields 按登记版本与当前完整字段 JSON 值比较。A→B→A 可使当前比较不再过时，但已发请求不撤回；整体替代始终过时。完整字段比较规则以[主设计第 3.5 节](design-v1.2.md#35-字段级依赖与强制登记mvp)为准。

①对需依赖类型的新建、更新及无变化 Update 强制同批完整登记，检查存在/引用/权限/新鲜度和最终当前对象图无环；不自动继承，显式空集与缺登记不同。历史边不限制当前合法依赖；批内或并发成环整批拒绝并给出定位。能力名和 fields 的接口位置仍待契约同步。

## 3. 各模块处理条件

### 3.1 ①管理处理器

只消费归其职责的管理反馈：⑥已验证管理员身份并写反馈，①在执行时再次检查可信授权，完成登记/权限/启停等内部管理步骤，单写操作结果供⑥查询。稳定请求 id 保障重投可恢复，受理与生效分开，组件就绪后才成为可用的启用状态（enabled）。不让插件自己授权、不让任意反馈升级权限。

状态/结果通过系统记录查询，不新增事件类型；跨数据库、消费者和权限分发采用可恢复阶段，不承诺所有组件一个事务生效。应急阻断见插件设计，不作为绕过正常管理反馈的日常入口。

### 3.2 ③归属模块

| 收到 | 条件 | 行为 |
|---|---|---|
| 数据库被修改 | 声纹/GPS 当前尚无归属 | 按当前参考建立归属；人物未知建未命名对象，地点未知归全局未知地点 |
| 数据库被修改 | 反馈属③ | 纠正、确认、参考管理、地点创建、命名/改名、范围重新归属 |
| 请求重新判断 | 目标属于③且支持重判 | 按当前输入重判，保护用户确认归属；结果及完整依赖、完成记录同批提交 |

仅使用参考字段匹配的归属不因名字变化被判过时。用户确认保护不等于免交完成记录；无变化照常确认完成。

### 3.3 ④活动提取模块

| 收到/内部触发 | 行为 |
|---|---|
| 本模块定时器 | 指定范围，扣除已成功提取区间后提取 |
| 归④的用户反馈 | 手动提取/重提取、规则管理、单次规则、历史应用、建议审核及执行结果 |
| 目标为 rule_selection 的重判 | 查看全部当前有效规则，含新增、不含删除，保存选择结果与实际输入/候选依赖；新选中生成、不再选中替代自动产物/未审核建议、仍选中不额外重算产物 |
| 目标为 md 产物的重判 | 同一规则 id 使用当前版本；规则失效则替代产物及未审核建议，不自动改用其他规则 |

产物不直接依赖 `rule_selection`，按自己的活动/规则/全部范围归属及实际人物地点字段依赖处理。手动应用产物不因自动不适用而撤销；若自己收到重判且规则已失效，仍执行失效处置。④不绕开⑤直接响应归属变更重算产物，也不因此重划活动。

### 3.4 ⑤依赖分析模块

| 输入 | 行为 |
|---|---|
| 普通新原始数据 | 不作为已有依赖失效的重判触发；③等各自处理新增数据 |
| “重新判断其他相关记录”反馈 | 按反馈指定的纠正前后对象查相关过时依赖 |
| 规则编辑通知 | 不主动扫历史；由其他输入触发时发现额外规则变化 |
| 被历史门控拦截的参考变化 | 不触发对应历史重判 |
| 当前语义结果/归属/插件结果修改、整体替代 | 查询当前有效目标及实际过时依赖，按上游等待和类型登记请求重判 |
| 完成记录查询结果（非新事件） | 推进完成目标的下游，或记录失败、超时、停用阻塞 |

新数据仍可由获授权插件按其业务订阅处理，不能把⑤对新原始数据的重判筛选推广为插件永不处理新增。

### 3.5 ⑥与插件

⑥必须接收获准的外部建议状态变化，以执行已批准且具备安全执行条件的动作；先核对当前状态及执行恢复信息。反馈/管理状态展示可查询相应记录，业务刷新按需订阅。执行后写反馈由④更新建议，不跨所有权直接修改。

插件只处理获授权的订阅和自己类型的重判请求；可重判插件与③④遵守同一完成记录机制。插件建议/执行反馈的交接结构待契约设计，不能据此赋予插件写④数据的权限。⑧未来处理获准产物变更来更新索引。

## 4. 重判完成、上游等待与持续输入

- ③、④和每个可重判插件各自单写其结果系统记录。记录表达请求 event_id、目标、变化/无变化/不适用/失败、前后版本、额外起因、root/depth/time/error；新增类型/英文枚举未冻结。
- 成功结果与业务写入、完整依赖刷新、`MarkProcessed` 同批；无变化也提交依赖和完成记录。业务不变不发修改事件，⑤通过①轮询结果而不是只等事件。
- 已知相关受影响上游可并行，下游等待这些上游完成；尽量合并多原因但保留全追溯。不能因为某一路无变化就丢掉另一条仍有效的原因。
- 可重试错误先重试，耗尽或不可恢复才记失败；崩溃没有完成记录属于等待/超时。失败、停用、超时阻塞下游，旧结果保留并标过时/无法更新，不冒充成功。
- 新变化在计算时到达，①提交检查依赖新鲜度，冲突需重读重算。不是全局暂停输入，不保证持续变化下只重算一次。
- ①强制当前对象 DAG，支持跨插件与插件内部任意有限层数；md 产物不是固定终点。有限工作集在没有新输入时完成或进入明确阻塞/失败；持续输入可持续产生新任务。
- 路径无下游，或结果没变且没有继续影响该路径时停止；安全限额必须记录/提示，不能把截断当成功。

## 5. 仍在模块内完成的步骤

| 步骤 | 模块与边界 |
|---|---|
| 定时器、归属前置检查等待/放弃 | ④内部，不新增总线事件 |
| 纠正时同步参考与归属 | ③构造同批写入，①保证批次校验与提交 |
| 产物变更、未审核建议替代/重生成 | ④处理；已批准/执行中/未知/已执行/已拒绝建议不被当作未审核 |
| 人物无参考/无声纹的清理判断 | ③决定是否整体替代，①执行终止版本语义，下游仍按依赖处理 |
| 计算及模型调用 | 业务模块计算，经⑦调用；⑦经①写metadata调用记录，不发事件 |
| 管理反馈执行 | ①内部管理逻辑，可恢复阶段与结果查询，不HTTP自调 |

## 6. 准确流程示例

以下是目标行为流程，不是已实现协议示例。未列出的消费者仅在其订阅获授权且相关时收到通知。

### 6.1 新数据与定时/手动提取

1. ②按去重键向①写声纹/GPS等原始数据，①提交后按授权订阅投递变更。
2. ③查当前无归属才计算，按匹配/未知对象规则写结果及完整依赖。重复事件不重复建立对象或归属。
3. ④定时器触发，或⑥写手动提取反馈由④消费；前置检查未全部归属则延后，超过等待上限提示放弃。
4. ④仅用原始转写/时间/GPS/手机数据划分活动并写名称描述，再读取适用规则判断所需的真实输入，保存选择结果，生成产物和建议。
5. 写入④所拥有结果及对应依赖；人物地点输入字段和活动范围全部归属不能漏登。手动重提取则按R6替代旧活动/产物，并让其已有下游由⑤继续调度。
6. ⑥按权限显示结果；有订阅的插件可处理新增活动/产物，但不得因此批量生成未授权的历史结果。

### 6.2 纠正归属、多原因与无变化完成

1. 用户把A从甲纠正为乙，⑥写反馈F；①按授权投递给③。
2. ③同批更新甲/乙参考及A归属：参考变化不自动扫历史归属，A归属变化可传播，根源为F、深度0。
3. ⑤查过时目标，可能包含选择结果、P1/P2/P3及插件结果；先收集已知相关上游，合并目标的多原因，记录全部追溯。不存在活动重划任务。
4. ⑤在目标相关上游就绪后发请求。④若重判产物，读取同一规则当前版本；发现规则变化作为额外起因，若已失效按终止处置，不换另一规则。
5. ④经⑦调用携带请求关联；P1/P2变更、P3不变。各请求的业务结果、完整依赖、完成记录及消费标记按批提交；P3无业务版本/事件但有完成记录。未审核建议按产物变化处理。
6. ⑤轮询确认P1/P2/P3完成，继续其确实受影响的插件下游；某路无变化不否定其他起因。失败/超时保留受阻状态，不发布虚假的全部完成。
7. ⑥展示处理状态和“同时重新判断其他相关记录”按钮；模型记录在①统一查询，⑦默认不存调用正文。

### 6.3 参考门控与多层插件链

用户点击上述按钮时，⑥写含纠正前后对象的反馈G，⑤消费并查过时归属；用户直接管理参考且选择重判时，③写放行的参考变化，⑤据此查依赖。若用户未选择，参考历史重判不启动。

```text
受影响归属V2、V3、V9并行重判（用户确认归属受保护）
  → 变化或无变化均提交完成记录
  → ⑤等待相关归属完成，调度受影响的核心产物
  → 产物完成后调度插件A结果
  → 插件B及插件A内部下层结果按DAG推进
  → 无下游或本路径无进一步影响时结束；有失败则明确受阻
```

各层仅写自己的类型。⑤不限制插件层数为一两层；①拒绝直接、间接和自环。无变化完成也能释放等待，但不凭空制造下游变化；持续有新输入则可有后续轮次。

### 6.4 选择结果和产物独立处理

1. 活动相关输入变化，使已登记依赖的 `rule_selection` 过时，⑤按其上游就绪条件请求④重判。
2. ④查看全部当前有效规则：新增适用规则R2生成产物；不再适用R1替代相应自动产物及未审核建议；仍适用R3仅保留选择，不额外请求其产物重算。
3. R3产物若自己的输入依赖过时，另按自己的重判路径处理；它不直接依赖选择结果。手动应用产物不因自动选择排除而撤销。
4. 若同一轮另有产物请求、并发规则编辑或替代，执行前查当前状态并在提交时校验；候选集合缺失/新增的并发保护方案待实施验证，不声称已有冻结契约解决。

### 6.5 审核、执行与外部结果未知

1. 用户在⑥通过建议S，⑥写审核反馈，④更新建议后由①投递变更。
2. ⑥查当前批准状态、执行记录与恢复信息，使用稳定动作标识及外部可靠幂等机制（若该系统提供）执行。
3. 查证已经成功则不重复；明确尚未执行才允许自动重试；调用超时、断线或外部成功但回写前崩溃等无法确定结果时，停止自动重试并提示用户核对。
4. 用户可确认已执行，或在提示可能重复后明确选择重试。⑥写执行/核对反馈，④更新建议；执行中/未知不是未审核状态，不随产物变化作废重做。
5. 外部标识允许用于恢复，具体保存方式待设计；本地查状态无法单独保证任意外部 exactly-once。插件动作也必须走审核，所有权交接格式待契约同步。

### 6.6 插件管理反馈、启停与补处理

1. 管理员在⑥轻量页面/API提交注册、权限、启停或凭据操作；⑥验证管理员，写管理反馈，返回已受理而非已生效。
2. ①持久化反馈并投递相应 `data_changed`，①管理处理器消费并复核身份/授权，调用内部逻辑，用稳定请求标识推进可恢复阶段。
3. ①单写登记、权限和操作结果，①⑤动态发现配置；消费者及权限等就绪后才启用。⑥查询结果，不引入第三种事件或依赖①重启。
4. 首次启用只自动处理启用后变化；需要历史批量产出由用户选择范围。主动停用阻止新访问/投递，不撤销已提交写入、不删除结果。
5. 主动停用后恢复提示漏过变化并由用户补或跳；意外断线/重启自动续处理。补处理读取当前状态，跳过不把旧结果标成最新。撤权后旧结果保留并显示无法更新。
6. 游标/snapshot交接、消费者恢复细节见实施计划，不能把这些目标写成已有接口；可信插件独立进程不等于安全沙箱。

## 7. 同步边界与局部验收

本轮仅更新设计文本。后续须对齐：版本不可变与终止事件、字段依赖及强制登记、动态注册/权限/管理反馈、完成记录、多 cause/根源追溯、插件建议交接、服务协议和恢复。准确字段、类型、枚举与日志保留参数仍待契约/实施设计，见[实施计划](../../ai-docs/plans/mvp-implementation.md)。

验收至少覆盖：重复事件与并发提交；无变化完成推进；上游失败/超时/停用阻塞；纯Markdown改名；规则最新版本及失效；选择结果与产物独立；多层DAG与持续输入；授权投递及所有读取入口过滤；外部未知结果；管理已受理与已生效分离。本文不把目标验收描述为已运行通过。
