# Ear 设计文档 v1.1（定稿）

> 定稿日期：2026-10-26
> 配套文档：《Ear MVP 工作分解》
> v1.1 变更：模块改名（归属模块、活动提取模块、依赖分析模块）；"级联"相关术语统一为"依赖分析"，"对应关系"统一为"归属关系"；新增【以后】检索索引模块。

## 0. 阅读说明

### 0.1 标记

| 标记 | 含义 |
|---|---|
| **【MVP】** | 学期末原型要实现，并且有验收标准 |
| **【预留】** | MVP 不实现，但现在的设计要给它留好位置，不能把路堵死 |
| **【以后】** | 产品以后要做的功能；MVP 不实现，只记录方向 |

### 0.2 文档范围

- 本文只规定**模块边界、模块之间交接的内容、产品行为和验收标准**。
- 模块内部怎么实现（选型、算法、提示词、表结构、阈值等）由负责的同学决定。
- 分工见《工作分解》。

### 0.3 总原则

- 只做 MVP，不追边角情况。
- **用确定的方法算出的结果，和推断出的结果分开存放。**
- **会影响历史结果的操作，一律由用户主动发起。** 系统不会自己回头修改历史。
- **用户纠正或确认过的结果，系统不会推翻。**

### 0.4 术语

| 术语 | 含义 |
|---|---|
| 归属关系 | 一条原始数据（声纹、GPS 点）属于哪个语义对象（人物、地点） |
| 依赖分析 | 某条信息被修改后，找出所有依赖它的信息并重新判断的机制 |
| 参考 | 用户认可的、用来认出某个人物或地点的原始数据 |
| md 产物 | 从活动中提取出的 Markdown 文本，例如笔记、待办 |
| 外部动作建议 | 从活动中生成的、待用户审核的外部操作，例如写入日历 |
| 根源反馈 | 引起一连串修改的最初那条用户反馈 |

## 1. 产品概述

Ear 是一个面向个人的活动建模服务。它从多个渠道持续收集用户的个人信息，比如录音、GPS、手机信息、邮箱等，把每一天整理成一连串活动，并记下每个活动涉及的人物、地点和内容。然后，Ear 按用户用自然语言设定的规则加工这些活动，输出笔记、待办、日历条目、提醒事项等结果。用户纠正一处错误后，所有受影响的结果都会自动修正，不需要逐条手动修改。

### 1.1 功能特性

- **多数据源**：每个渠道的数据都由各自的适配器转换成统一格式。增加渠道时只需新增适配器，其他部分不用改。【MVP】录音、GPS、手机信息；【以后】邮箱等。
- **活动建模**：自动把一天划分为若干活动，并认出其中的人物和地点。认不出的人会归为"未命名人物"，同一个陌生人多次出现时能归到一起。
- **原始数据与语义信息分开存放**：用确定方法算出的结果（声纹、定位），和推断出的结果（人物、地点、活动）分开存放。原始数据只追加、不修改；语义信息保留完整的修改历史。
- **自然语言规则**：用户用自然语言说明"什么样的活动、提取什么内容"。规则可以针对一类活动，也可以只针对某一个活动。规则只对以后的活动生效，用户也可以手动把它用在过去的活动上。
- **多输出渠道**：md 产物（笔记、待办）直接保存；外部动作（写入日历、提醒事项）先生成建议，用户确认后才执行。
- **依赖分析**：纠正一处后，依赖它的结果自动更新。修改的传播一定会停止，每一步都能追溯到最初那次纠正。
- **由用户掌控**：用户纠正或确认过的结果，系统不会推翻；影响历史结果的操作，都由用户主动发起。
- **可扩展**【预留】：扩展模块可以读取数据、汇总多个活动的信息，并自动参与依赖分析。
- **供其他 Agent 检索**【以后】：md 产物切片后存入向量数据库，供其他 Agent 通过 RAG 调用。
- **私有部署**：每个用户独立部署一套服务，数据完全归用户自己所有。

### 1.2 范围

- 【MVP】学期末做出能实际运转的原型，跑通第 12 节的端到端流程。
- 【MVP】**一人一套**：每个用户自己部署一套服务端，人物、地点、规则互不相通。每套服务端只服务一个用户，客户端只用一个访问令牌防止外人访问。
- 【以后】多用户：即使以后支持多个用户，每个用户的数据也完全分开，人物库、地点、规则都不共享，效果上等于多套独立的单人服务。
- 【预留】原始数据的来源字段里记下"来自哪个用户"。以后如果在同一套服务端上支持多个用户，可以用它来隔离各人的数据。

## 2. 总体架构

### 2.1 模块

| 编号 | 模块 | 职责 |
|---|---|---|
| ① | 存储与事件 | 数据库、总线、统一读写接口、依赖登记与查询 |
| ② | 适配器 | 把外部数据转成统一输入格式并入库 |
| ③ | 归属模块 | 声纹 → 人物，GPS 点 → 地点，维护参考 |
| ④ | 活动提取模块 | 定时和手动提取、划分活动、选规则、生成 md 产物和外部动作建议 |
| ⑤ | 依赖分析模块 | 找出受影响的信息，请求重新判断，控制传播，记录传播过程 |
| ⑥ | 客户端与 API | 界面、用户反馈、执行外部动作 |
| ⑦ | 大模型入口 | 所有大模型调用的统一入口，记录每次调用 |
| ⑧ | 检索索引模块【以后】 | md 产物切片、向量化，供其他 Agent 检索 |

- 【MVP】模块之间的业务通信一律经过总线（事件驱动）。
- 【MVP】读写数据库（①）、调用大模型（⑦）属于基础设施，直接调用，不经过总线。

### 2.2 数据流

```
外部文件 ──► ② 适配器 ──写入──► ① ──「数据库被修改」──┬──► ③ 归属模块（新的声纹、GPS 点；归它处理的用户反馈）
                                                         ├──► ④ 活动提取模块（归它处理的用户反馈）
用户操作 ──► ⑥ 写用户反馈 ──► ①                         ├──► ⑤ 依赖分析模块（已有语义信息被修改）
                                                         ├──► ⑥（刷新界面，可选）
                                                         └──► ⑧ 检索索引模块【以后】（md 产物变化）

④ 内部定时器 ──► 定时提取

⑤ ──「请求重新判断」──► 按登记表分发给负责模块（MVP：③、④）

④ 生成外部动作建议 ──► ⑥ 展示 ──► 用户审核 ──► ⑥ 执行外部动作 ──► 执行结果写回为用户反馈
```

## 3. 数据

### 3.1 数据分类【MVP】

| 类别 | 内容 | 规则 |
|---|---|---|
| 原始数据 | 录音引用、转写段、局部说话人、声纹、环境声、GPS 点、手机信息、用户反馈 | 由确定的方法得出；**只追加，不修改** |
| 语义信息与归属关系 | 人物（含参考）、地点（含参考）、活动、md 产物、外部动作建议；声纹 → 人物、GPS 点 → 地点 | 由推断得出；可以修改 |
| 提取规则 | 适用范围、提取内容、可选动作 | 只对以后生效 |
| 系统记录 | 依赖登记、提取记录、传播记录、大模型调用记录、事件日志等 | 不发事件 |

- 不使用置信度。
- 声纹、转写等由 Ear 用传统模型确定地算出，所以算原始数据。

### 3.2 id 与版本【MVP】

- 语义信息、归属关系、规则都有一个**永远不变的 id**。每次修改都生成一个新版本，旧版本标记为"已被替代"并保留。
- 依赖按"对象 + 版本"登记，以便判断依赖是否已经过时。
- md 产物、活动名称和描述里提到人物或地点时，**只存 id，显示时再换成当前的名字**。
- 验收：**改名不会引起任何重新归属或重新提取。**
- MVP 没有合并对象的操作，所以 id 没有例外。

### 3.3 统一输入格式【MVP】

每条原始数据至少有以下字段：

| 字段 | 说明 |
|---|---|
| id | 数据的唯一标识 |
| 类型 | 声纹、GPS 点、转写段、用户反馈等 |
| 事件时间区间 | 数据描述的时间段；单个点的起止时间相同 |
| 入库时间 | 和事件时间分开记 |
| 来源 | 设备、渠道、用户 |
| 适配器版本 | 例如 Ear 的模型版本。重新处理会产生一批新数据，旧数据保留 |
| 去重键 | 由适配器计算，例如"设备 + 文件哈希值"。已有相同的键就跳过，保证同一份数据无论送进来多少次都只存一条 |
| 数据 | 具体内容；大文件只存引用（路径 + 哈希值） |

### 3.4 需要归属的原始数据【MVP】

- **声纹**：要归属到人物。
- **GPS 点**：要归属到地点。不设"停留段"，GPS 每隔一到几分钟采一个点，间隔由适配器负责人决定。
- 其他类型（转写、手机信息、用户反馈等）不需要归属。

**状态规则**：需要归属的数据，只有刚写入、还没处理时可以没有归属对象；**处理过的一定有归属对象**。"有没有归属对象"就是"处理过没有"，不另设状态字段。

### 3.5 适配器【MVP】

- **声音适配器**：封装现有的 Ear 基础处理模块（保留，不重写），输出录音引用、转写段、局部说话人、声纹、环境声。
- **GPS 适配器、手机信息适配器。**
- **扫描服务**：发现 Octopus 目录中的新文件，交给对应的适配器。
- **用户反馈适配器**：属于 ⑥，见第 5 节。
- 【以后】更多输入渠道，比如邮箱、自研 App。按统一输入格式新增适配器即可，不影响其他模块。

## 4. 事件

### 4.1 总线上的事件【MVP】

总线上只有两种事件。字段可以增加，不能减少。

**「数据库被修改」**：写入原始数据、语义信息、归属关系、规则时，由 ① 自动发出；写入系统记录时不发。

| 字段 | 用途 |
|---|---|
| 数据类别、数据 id | 接收方据此判断要不要处理 |
| 操作：新增 / 修改 / 标记为已被替代 | 同上 |
| 新版本号、旧版本号 | 判断哪些依赖已经过时 |
| 根源反馈 id | 追溯到最初那次用户操作；定时提取等系统发起的行为标为"系统" |
| 依赖分析深度 | 保证传播会停 |
| 是否处理历史 | 门控：用户没有选择重新判断时，⑤ 跳过 |

**「请求重新判断」**：由 ⑤ 发出，按登记表分发给负责模块。

| 字段 | 用途 |
|---|---|
| 目标类别、目标 id | 要重新判断哪一条 |
| 起因：引起它的修改（类别、id、新旧版本） | 追溯 |
| 可读的修改描述，如"局部说话人 C：丙 → 丁" | 交给大模型使用 |
| 根源反馈 id、依赖分析深度 | 往下传；负责模块写入新版本时原样带上 |

### 4.2 事件规则【MVP】

- **事件里只带 id 和版本号，不带内容。** 需要内容的接收方，自己去 ① 查当前版本或任意历史版本。
- **内容没有变化时，不写入，也不发事件。**
- 接收方根据数据**当前的状态**判断要不要处理，不管事件是谁发出的。例如，一个新声纹被写入后，③ 看到它还没有归属对象，就去处理；⑤ 查不到任何依赖它的信息，就什么也不做。
- 验收：**同一个事件被送达多次时，结果和只送达一次相同。**
- 验收：**写入成功就一定发出事件，写入失败就一定不发。**

## 5. 写入权限与用户反馈

### 5.1 每类数据只有一个模块负责写【MVP】

| 模块 | 负责写的数据 | 执行哪些用户反馈 |
|---|---|---|
| ② 适配器 | 外部来源的原始数据 | — |
| ③ 归属模块 | 人物、地点、归属关系、参考 | 纠正、确认、增减参考、新建地点、命名或改名、按时间范围重新归属 |
| ④ 活动提取模块 | 活动、md 产物、外部动作建议、规则 | 手动提取或重新提取、规则的增删改、只改这一次的提取、把规则应用到历史活动、审核建议、外部动作的执行结果 |
| ⑤ 依赖分析模块 | 传播记录 | — |
| ⑥ 客户端与 API | 用户反馈 | — |

### 5.2 用户反馈的流程【MVP】

1. 用户在界面上操作。⑥ 把操作转成**结构化的用户反馈**，存为原始数据。
2. ① 发出「数据库被修改」。负责这类反馈的模块读到它，执行修改。
3. 由这次反馈引起的所有修改，都带上它的 id 作为根源反馈 id。

- 修改是异步完成的。界面要有"处理中"状态，怎么显示由 ⑥ 决定。
- 用户反馈的具体格式由 ⑥ 与 ③、④ 共同约定。
- 【以后】用自然语言纠正，比如"那天说话的不是甲，是乙"。由大模型把它解释成结构化修改，先作为建议请用户确认，确认后再按结构化反馈执行。

## 6. 归属模块（③）

### 6.1 处理新数据【MVP】

触发条件：需要归属的数据还没有归属对象。

- 如果这条数据已经是某个对象的参考，就归属到那个对象。
- 否则和所有有参考的对象比较：
  - **人物**：匹配上就归属到这个人物。匹配不上就**新建一个未命名人物**，并把这条声纹设为它的第一个参考。这是系统唯一一次自动设置参考。
  - **地点**：匹配上就归属到这个地点。匹配不上就归属到全局唯一的**"未知地点"**。它的意思是"这只是一个零散的定位点"，它没有参考，也不参与匹配。
- 第一次建立归属关系时，还没有其他信息依赖它，所以不会触发依赖分析。
- 匹配算法、阈值、依赖里登记哪些候选，由负责人决定。

### 6.2 参考【MVP】

- 人物的参考声纹、地点的参考点，都由**用户**维护。系统只在新建未命名人物时自动设置一次。
- 用户**纠正**归属关系时，这条数据从原对象的参考中移除，加入新对象的参考，同时归属关系改为新对象。
- 用户**确认**归属关系时，这条数据加入当前对象的参考。
- **一条数据最多只作为一个对象的参考。**
- 验收：**用户纠正或确认过的数据，任何重新归属都不会改变它的归属结果。**

### 6.3 门控：参考改了之后，要不要重新判断以前的归属关系【MVP】

- 一律由用户主动选择，系统不会自动回头修改历史。
- 在人物或地点页面管理参考时：系统询问用户。
- 纠正之后：不弹窗，结果旁边放一个"同时重新判断其他相关记录"按钮。
- 用户选择重新判断后，⑤ 按依赖找出受影响的归属关系，交给 ③ 重新判断。
- 验收：以前曾把这个对象当作主要候选的归属关系，都能被找出来。
- 依赖查不到的情况（比如新建的对象以前从未当过候选），用独立功能"**按时间范围重新归属声纹或 GPS 点**"来补。

### 6.4 未命名人物与地点【MVP】

- 某个人物的参考全部被移走后，这个人物保留，但不再参与匹配。
  - 名下还有声纹：提示"#N 还有 M 段声音，可能也是 X"，并提供"重新判断"按钮。
  - 名下已经没有声纹：标记为"已被替代"。
- 地点**只能由用户手动创建**：在时间线或地图上选中一些 GPS 点，这些点成为新地点的参考，同时改为归属到新地点。

### 6.5 以后的功能

- 【以后】合并人物。MVP 里同一个人被拆成多个未命名人物时，先用增加参考、重新判断来补救。
- 【以后】系统自动建议新建地点，比如"这里你常来，要不要建成一个地点？"。可以直接接入建议机制。
- 【以后】重新归属的结果和用户的判断不同时，生成一条提示请用户确认。

## 7. 活动提取模块（④）

### 7.1 触发【MVP】

- 只有两种方式，每次都要有一个时间范围：
  - **定时**（如每晚 9 点），定时器在 ④ 内部。
  - **手动**：作为一种用户反馈，由 ⑥ 写入。
- 定时提取的范围：从上一次成功的定时提取结束的时刻，一直到现在，**并去掉已经成功提取过的时间段**（不管那次是手动还是定时）。被放弃的提取不算提取过。
- 验收：定时提取不漏时间段，也不覆盖已经成功提取过的时间段。
- 【以后】自动触发，比如录音结束时、检测到长时间安静时。

### 7.2 流程【MVP】

1. **前置检查**：这段时间内需要归属的数据，都已经有归属对象。没有就延后重试，超过等待上限就放弃，并提示用户。
2. **划分活动**：由大模型把这段时间划分成若干活动。**活动不依赖归属关系**，所以纠正"A 是乙"不会让活动重新划分。
3. **选规则**：由大模型根据规则写明的适用范围，判断每条规则适不适用于这个活动。
4. **提取**：按选中的规则生成 md 产物。
5. **登记依赖（粗粒度）**：每条 md 产物依赖它所属的活动、所用规则的版本，以及活动时间范围内的**所有**归属关系。
6. **生成外部动作建议**：规则带有动作时生成（见 7.6）。

- 验收：能处理一整天的数据，中间不失败。怎么处理长数据，由负责人决定。

### 7.3 重新提取【MVP】

- 用户手动对某段时间重新提取时，这段时间里的旧活动和旧 md 产物全部标记为"已被替代"，新活动使用新的 id。
- 执行前提示用户："有 N 个活动带有你的修改，重新提取后这些修改将失效。"
- 【以后】由大模型判断新活动是不是旧活动的延续，沿用旧 id，并把旧活动上的修改迁移过来。

### 7.4 规则【MVP】

- 用自然语言写明**适用范围、提取内容、可选动作**。适用范围可以带条件，比如"本实验室、有某位老师参加的组会"，是否适用都交给大模型判断。
- "**只改这一次提取**"也作为一条规则存储，它只适用于某一个活动，创建后立即对这个活动执行提取。
- 规则的新增、修改、删除**只对以后的活动生效**，以前的结果不受影响。
- 用户可以手动把某条规则应用到某个历史活动上。这时跳过选规则这一步，提取结果追加到这个活动的已有 md 产物后面。

### 7.5 md 产物格式【MVP】

| 字段 | 说明 |
|---|---|
| 产物 id、版本号 | |
| 所属活动 id | |
| 规则 id、规则版本 | |
| 来源 | 选规则后自动提取 / 用户手动应用到这个活动 |
| 正文 | Markdown 文本。人物和地点写成引用标记 `[[person:<id>]]`、`[[place:<id>]]` |
| 生成方式、根源反馈 id | 首次提取或依赖分析；如果来自依赖分析，记下最初由哪条用户反馈引起 |

- 活动的名称和描述也用同样的引用标记。⑥ 只需实现一套显示逻辑：把标记换成当前的名字。

### 7.6 外部动作建议【MVP】

- 外部动作的类型由架构统一规定。MVP 只有两种：

| 动作 | 字段 |
|---|---|
| 写入日历 | 标题、开始时间、结束时间、备注 |
| 写入提醒事项 | 标题、截止时间、备注 |

- 规则里的可选动作，只能从上表中选。
- 流程：④ 生成建议 → 用户在 ⑥ 审核 → 审核通过后由 ⑥ 执行 → 执行结果写回为一条用户反馈 → ④ 更新建议的状态。
- 每条建议记下它来自哪条 md 产物的哪个版本。md 产物有了新版本后，**还没审核的旧建议标记为"已被替代"，再按新版本重新生成**。已通过、已执行、已拒绝的建议都不动。
- **外部动作执行后视为用户已确认**，以后不再修改，也不记录它在外部系统里的 id。
- 审核通过的建议所对应的 **md 产物本身照常参与依赖分析**。用户审核时确认的是"执行这个动作"，不是"产物内容正确"。所以 App 里的 md 产物可能和外部系统里的条目不一致。
- 【以后】新增外部动作类型，每接入一个外部系统就加一种。
- 【以后】已执行的外部动作和 md 产物不一致时，提醒用户同步。

### 7.7 重新判断【MVP】

- 收到「请求重新判断」后，按**同一条规则，带上旧版本和修改原因**，重新提取指定的 md 产物。
- 验收：**修改没有影响到的 md 产物，重新判断后的输出必须和旧版本完全相同。**这样"内容没变就不写入"可以靠逐字比较来判断，传播记录里也只留下真实的修改。

### 7.8 以后的功能

- 【以后】问答与按需补充：用户提问时先查 md 产物，查不到再回到转写去找，答案写回为这个活动的 md 产物。可以把"一次提问"作为一条只改这一次的规则，接入现有机制。⑧ 检索索引模块实现后，"先查 md 产物"这一步可以直接用它。
- 【以后】细粒度依赖：每条 md 产物只依赖它实际用到的信息。只需替换登记依赖这一步，依赖分析的机制不变。
- 【以后】补传数据的检测（提取完成后才到达的数据）、跨越定时触发时刻的活动。
- 【以后】用户直接修改活动（改名、调整边界、拆分、合并），直接编辑或删除 md 产物。

## 8. 依赖分析模块（⑤）

### 8.1 流程【MVP】

1. 收到"已有的语义信息被修改"的「数据库被修改」事件。事件标记了"不处理历史"时跳过。
2. 通过 ① 查出依赖被修改对象、且登记的版本已经过时的归属关系和 md 产物。
3. 查出修改前后两个版本，生成可读的修改描述，然后对每一条发出「请求重新判断」。
4. 负责模块重新判断。结果有变化才写入新版本，写入时再发出事件，回到第 1 步。
5. 记录完整的传播过程：根源反馈、每一步的起因和目标、结果有没有变化、在哪里停下。

### 8.2 一定会停的原因【MVP】

- 没有任何信息依赖 md 产物，所以修改最多传到 md 产物。
- 已执行的外部动作不参与依赖分析。
- 活动不依赖归属关系。
- 参考只能由用户修改；要不要重新判断以前的归属关系，也由用户触发。
- 内容没有变化时，不写入，也不发事件。
- 另设兜底手段（比如深度上限），防止实现出错时无限循环。具体方式由负责人决定。

### 8.3 验收【MVP】

- 依赖被修改对象的信息，一条不漏地被找出来。
- 任何一次修改引起的传播，都在有限步内停下。
- 每一次修改都能追溯到最初的那次用户操作。
- 一条传播记录能和它引起的所有大模型调用关联起来（配合 ⑦）。

### 8.4 分发方式

- 【MVP】⑤ 按"**数据类型 → 负责模块**"的登记表分发「请求重新判断」。MVP 登记表里只有：归属关系 → ③，md 产物 → ④。
- 【以后】研究**会形成环的依赖分析**，比如 md 产物反过来帮助认人（"会上有人喊了'甲老师'"）。到那时，置信度、传播策略才有研究意义。现在的结构里没有环，传播一定会停。

## 9. 大模型入口（⑦）【MVP】

- 基于 Octopus 现有的大模型接入部分，独立成一个 docker 服务，后端对接反代平台。
- 各模块调用大模型都必须经过它，并带上**调用方模块**和**根源反馈 id**。系统发起的调用（如定时提取）标为"系统"。
- 每次调用都要记录：用途、用量、耗时。这些记录用于报销统计，也是论文的实验数据。
- 换模型、限流、重试都在这里统一处理。
- 验收：用量可以按模块、按根源反馈统计；没有带调用方模块的调用会被拒绝。

## 10. 扩展性

一个扩展就是一个新的模块，比如社交扩展（汇总某个人的相关活动）、习惯扩展（从活动中总结习惯）。提取规则针对的是**单个活动**，扩展针对的是**跨活动的汇总**，两者不重叠。

### 10.1 扩展约定

| 约定 | 标记 |
|---|---|
| 扩展通过 ① 的读取接口读数据，订阅「数据库被修改」，经过 ⑦ 调用大模型 | 【预留】 |
| **单向依赖**：扩展可以依赖核心数据，核心数据不能依赖扩展的数据 | 【预留】 |
| 扩展只能写自己的数据类型；要改核心数据，只能生成建议或用户反馈 | 【预留】 |
| 扩展在登记表中登记自己的数据类型，并登记依赖，就能自动参与依赖分析 | 【预留】（登记表本身是【MVP】） |
| 扩展的输出沿用 md 产物格式：Markdown 加引用标记 | 【预留】 |
| ① 的读取接口和事件格式，作为对外公开的约定来维护 | 【预留】 |
| ⑥ 提供一个通用的扩展页面，用来显示扩展的输出 | 【以后】 |
| 具体的扩展（社交、习惯等） | 【以后】 |

### 10.2 检索索引模块（⑧）【以后】

把 md 产物切片后存入向量数据库，供其他 Agent 通过 RAG 调用。按 10.1 的扩展方式接入，不改动任何已有模块。

- **接入方式**：订阅「数据库被修改」。md 产物出了新版本、或被标记为"已被替代"时，更新对应的索引。
- **只写自己的数据**（向量索引）；其他模块都不依赖它。外部 Agent 只读，想改东西只能通过建议或用户反馈。
- **不参与依赖分析**：切片和向量化是确定的计算，不是推断，所以不登记依赖，也不接收「请求重新判断」。md 产物因依赖分析而变化时，索引会跟着事件自动更新。
- **只索引 md 产物**，不索引外部动作建议。
- 验收标准（初稿）：
  - 索引里只有每条 md 产物的**当前版本**。产物经依赖分析修改或重新提取后，检索不到旧内容。
  - 检索结果带上产物 id、版本、活动 id 和时间范围，Agent 可以据此通过 ① 读取完整产物。
  - 能按人物名字检索到相关内容。改名后，检索结果显示新名字，用新名字也能检索到。
  - 支持按时间范围、人物、地点过滤。
- 改名后需要重新向量化，这是 ⑧ 内部的确定计算，和"改名不会引起任何重新归属或重新提取"不冲突。
- 切片方式、向量库选型、引用标记的处理方式，由负责人决定。

## 11. 用户可以做的修改【MVP】

"触发依赖分析"指这项修改会引起依赖它的信息重新判断。

| 对象 | 修改 | 执行模块 | 触发依赖分析 |
|---|---|---|---|
| 人物 | 纠正归属关系 | ③ | 会 |
| | 确认归属关系 | ③ | 不会（结果不变） |
| | 增减参考声纹 | ③ | 仅当用户选择重新判断 |
| | 命名、改名 | ③ | 不会 |
| 地点 | 新建地点 | ③ | 会 |
| | 纠正归属关系 | ③ | 会 |
| | 确认归属关系 | ③ | 不会 |
| | 增减参考点 | ③ | 仅当用户选择重新判断 |
| | 改名 | ③ | 不会 |
| 规则 | 新增、修改、删除 | ④ | 不会（只对以后生效） |
| | 只改这一次的提取 | ④ | 不会（立即提取并追加） |
| | 把规则应用到历史活动 | ④ | 不会（追加） |
| 输出 | 审核外部动作建议 | ④ | 通过后由 ⑥ 执行，执行后不再修改 |
| 批量 | 按时间范围重新归属 | ③ | 结果有变化时会 |
| | "同时重新判断其他相关记录" | ⑤ → ③ | 会 |
| | 手动提取或重新提取某段时间 | ④ | 不会（替换） |

【以后】合并人物、隐私控制（标记"不追踪"、屏蔽或删除某个人的数据）、直接修改活动、直接编辑或删除 md 产物、用自然语言纠正。

## 12. 端到端验收【MVP】

### 12.1 数据

- **判定是否通过：用模拟组会。** 组员按脚本录制，标准答案事先确定：谁在什么时候说话、活动边界、应该提取出的待办、应该生成的建议、在哪里。这份数据也用作回归测试和学期末演示。
- **检查可靠性：用真实数据。** 只验收"能连续跑完一整天，中间不失败"，也供各模块调参，不作为判定标准。
- 辅助数据：真实数据上的标注（人物、活动边界），用于检验 ③ 和 ④；规则测试集（应该触发和不应该触发的例子），用于检验 ④。

### 12.2 流程

| 步骤 | 内容 | 模块 |
|---|---|---|
| 1 | 组会录音和 GPS 入库 | ② |
| 2 | 声纹归属到人物，GPS 点归属到地点 | ③ |
| 3 | 定时提取：划分出组会活动，生成笔记、待办等 md 产物，以及"写入提醒事项"的建议 | ④ |
| 4 | 在 App 里看到时间线和 md 产物 | ⑥ |
| 5 | 纠正"A 不是甲，是乙" | ⑥ → ③ |
| 6 | 待办负责人改为乙；未审核的建议重新生成；和这次纠正无关的 md 产物保持不变 | ③ ④ ⑤ |
| 7 | 审核通过建议，手机提醒事项里出现正确的内容 | ⑥ → ④ |
| 8 | 能查出这次纠正引起的完整传播记录，以及过程中的每次大模型调用 | ⑤ ⑦ |
