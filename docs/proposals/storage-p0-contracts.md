# 提案：① P0 首批契约选择（字段依赖、登记表能力、批末检查）

> **状态：accepted（推荐方案已采纳；尚未实现）。** 采纳依据是项目负责人（用户）明确表示：采用推荐方案，允许在功能分支持续实现并分批提交、推送和提 PR；I 审核由负责人负责，合并前再审核。这是对本文推荐选择的采纳和对功能分支实现的授权，**不是合并前的人工审查已经完成**：本文没有 `reviewed-by` / `reviewed-at`，AI 不代填，合并前审核由负责人兼 I 在 PR 中完成（见第 4 节）；CI 通过不等于审核通过。涉及③④的候选类型是否启用强制，仍按类型取得其实际输入并通知，见 2.9、2.11。目标行为已由[设计 §3.5](../design/design-v1.2.md#35-字段级依赖与强制登记mvp)和[决策索引](../decisions/mvp-confirmed-decisions.md)确定，本文只讨论接口形式、兼容方式和错误语义。第 2 节中的“推荐”即已采纳的选择，备选项只保留为理由和代价的记录；原先标为“暂拟”的名称和内部 API（如 `DependencyInput`、空集读取方式、能力项名称）属于合理的工程决定，由实现者定名，无需再等待确认，PR 中说明最终名称即可。`fields`、`requires_dependencies`、`rule_selection` 是已讨论过的术语。本文不冻结服务 HTTP 协议、API、凭据或数据库版本。

## 1. 现状要点

代码证据和定位见[①实施准备](../../services/storage/ai-docs/implementation-plan.md#2-当前能力与证据)。和本文相关的有：

- `VersionRef`、`DependencyRecord` 接受未知字段，但内存实现登记时只保留 `data_type/id/version`，`fields` 被静默丢弃。
- `RegisterDependencies` 要求被依赖方在**该操作执行时**是当前版本且未终止，否则返回冲突 `stale_dependency`；对整批执行完后的最终状态不再检查。
- 显式空集在内部存为空元组，但读取接口无法区分“登记过空集”和“从未登记”；重复登记空集每次都返回 `written`。
- 只拦截直接自依赖；`DataTypeSpec.from_json` 会丢掉不认识的能力项。

## 2. 推荐选择

### 2.1 `fields` 的位置

**推荐**：在 `DependencyRecord` 顶层增加可选的 `fields`，作用是修饰 `depends_on`（选择被依赖方 payload 的哪些顶层字段）。`VersionRef` 本身不变。

| 方案 | 代价 |
|---|---|
| 推荐：放在 `DependencyRecord` 顶层 | 旧读取方会把它当作未知字段保留并忽略，可以继续解析，但不会理解字段语义；所有读取路径和 SDK 必须原样保留它 |
| 备选：放进 `VersionRef.fields` | `VersionRef` 也用于 `dependent` 和 `StaleDependency`，在那些位置没有意义；还会和“对象 + 版本”的身份语义混在一起 |
| 备选：把 `depends_on` 改成嵌套结构 | 改变了现有字段的结构，不是加性变更 |

### 2.2 SDK 输入

**推荐**：新增显式输入类型（暂拟名 `DependencyInput`），携带一个 `VersionRef` 和可选的 `fields`。`RegisterDependencies.depends_on` 接受 `VersionRef` 和 `DependencyInput` 的混合序列。

- 直接传 `VersionRef` 的旧调用，语义完全不变：依赖整个对象，并且按严格模式检查（版本必须是当前且未终止）；`dependent` 的语义也不变。
- 在写入路径上，如果 `VersionRef` 带有额外的 `fields`，**推荐**以 `InvalidRequest` 拒绝，并提示改用 `DependencyInput`；不能再静默丢弃。这一点会改变一个目前可以通过的输入，已采纳，PR 中须写明这一行为变化。备选是继续忽略它，代价是调用方会误以为 fields 已经生效。

### 2.3 `fields` 规范化（落实设计 §3.5）

- 省略 = 依赖整个对象；`[]` 用 `InvalidRequest` 拒绝；去重后按字典序排序存储。
- 元素必须是字符串，按被依赖方 payload 的真实顶层键解释，允许任意字符串键（包括空字符串 `""`；与其他键一样，payload 中没有该键时按下面的“字段缺失”处理）。**不限制为 snake_case 或非空**：payload 的顶层键是任意 JSON 键，①不擅自收窄。空列表 `[]` 仍然拒绝（见上）。
- 登记版本中可以没有所选字段；“字段缺失”被记录下来，并且与 `null` 视为不同的值。

### 2.4 同一批中重复输入

同一次登记里，同一对象出现多次时：

- 版本相同：合并（已采纳）。其中任意一项是整个对象，就按整个对象处理；否则取所选字段的并集。
- 版本不同：以 `InvalidRequest` 拒绝。

现状是后一项静默覆盖前一项。合并规则已采纳；“重复即拒绝”是未选的备选。

### 2.5 新鲜度：旧模式不变，字段模式按字段值判断

| 输入 | 登记时 | 查询过时 |
|---|---|---|
| `VersionRef`（旧），或 `DependencyInput` 未指定 fields | **保持现状**：版本必须是当前版本且未终止 | 登记版本低于当前版本即过时 |
| `DependencyInput` 且带 fields | **已采纳**：登记版本中所选字段的 JSON 值与当前版本完全相同，并且对象未终止，即可接受（允许登记较旧的输入版本） | 所选字段的值有任一不同即过时；被依赖方整体替代后**始终**过时 |

推荐理由：例如③只用 `references` 完成计算，期间人物被改名，这时不应强制重读重算。代价：这**改变了现有 RegisterDependencies“依赖版本必须是当前版本”的语义**（仅对新的输入类型生效），不是加性修复，PR 中必须写明，并在合并前核对。备选是字段模式也要求当前版本，实现更简单，但并发改名会带来更多 `stale_dependency` 重试。

`DependencyInput` 未指定 fields 时等同于依赖整个对象，沿用旧模式的严格版本规则，不因换了输入类型而放宽。旧模式保持严格，实现不得悄悄放宽。

### 2.6 字段值比较

- 沿用当前 `canonical_json`（`json.dumps` 加排序键，**不是 RFC 8785**）。由①在服务中用同一函数计算，不依赖数据库的 json 相等判断；由内存与持久化后端共享的测试用例确保两者结果一致。
- 共享测试向量：`1` 与 `1.0` 不同；`True` 与 `1` 不同；对象键顺序无关；数组顺序有关；缺失与 `null` 不同；非 ASCII 字符串逐字比较。内存后端和持久化后端必须得到一致结果。
- 备选是改用 RFC 8785/JCS，代价是数字规范化会改变现有“内容无变化”的判定，不能当作加性改动。

### 2.7 读取模型与过时结果

- `DependencyRecord` 以及新的读取结果必须保留 `fields`，SDK 不得丢失。`StaleDependency` 增加可选的 `fields`；是否同时给出“发生变化的字段”由实现者决定。
- 读取模型继续接受未知字段。不能因为新增了能力项，就对读取模型全局禁止未知字段。

### 2.8 显式空集

**推荐**：把“已登记（哪怕是空集）”作为可读的事实。提供一种读取方式（名称暂拟），能区分“从未登记”和“登记为空集”；重复登记同一个空集时返回 `unchanged`。备选是只在内部记录，用于批末完整性检查；代价是⑤和排障时无法区分这两种情况。

### 2.9 登记表能力

- 保留 `writer` 的语义：所属模块就是重新判断的执行方，不另设执行人字段。
- 增加 `requires_dependencies` 以及是否支持重判的能力项（名称由实现者定）；from_json/to_json 往返不得丢失。
- **缺省为 false**，用于兼容旧的登记表文件；这**不表示**核心类型应当永久为 false。候选类型有 `attribution`、`artifact`、`rule_selection`（尚未登记），由③④负责人按实际输入确认后再启用，本文不擅自给所有核心类型开启强制。
- 一个类型属于核心还是插件，由**可信的注册来源**决定（内置核心配置，或①处理的动态插件登记），不能依靠 spec 中调用方自报的字段。内存实现的准确 API 由实现者定名。

### 2.10 批末检查和错误语义

| 检查 | 范围 | 推荐的错误 |
|---|---|---|
| 完整登记 | 需要依赖的类型执行 Create 或 Update（包括结果为 unchanged 的 Update）时，必须同批登记其结果版本的依赖；可以是显式空集；Supersede 不需要（[设计 §3.5](../design/design-v1.2.md#35-字段级依赖与强制登记mvp)） | `InvalidRequest`（请求本身不完整，重读也不会修好） |
| fields 格式、重复版本不一致 | 同上 | `InvalidRequest` |
| 新鲜度 | **只检查本批的登记或重算结果**，在批末按最终状态检查；同批中先登记、后更新被依赖方时，若为全对象模式（含旧 `VersionRef`），或字段模式下所选字段的值发生变化，会被拒绝；字段模式下只改动了无关字段、所选字段值仍相等的，按 2.5 的推荐规则可以接受。**不扫描、也不因此拒绝其他对象已有的过时依赖**，否则任何上游更新都无法提交 | 沿用 `stale_dependency`，details 中带上 fields |
| 当前图无环 | 只看当前版本且未终止的依赖方之间的边；拒绝经过本批登记边的自环、间接环和批内形成的环；旧版本的历史边不阻止新的图 | 新增冲突原因 `dependency_cycle`（已采纳；默认不可重试，details 中给出环路径，P1 再按权限过滤）；备选 `InvalidRequest` 未选 |
| 核心不能依赖插件 | 依赖方是核心类型、被依赖方是插件类型 | `InvalidRequest` |

保留现有登记顺序：`dependent_version=None` 取本批前面操作执行后的当前版本，不改成整批任意顺序。新增冲突原因属于公共枚举的扩充。当前 SDK 中 `Conflict.retryable` 按 `RETRYABLE` 集合判断，因此未知的原因字符串不会被列为可重试；但旧客户端在解码、枚举取值和分支处理上能否兼容未知原因**尚未证明**，需要用旧版本客户端做端到端兼容测试，不推定远程旧客户端已经支持。选择 `dependency_cycle` 已采纳；兼容测试在 P0b-3 实现，结果在合并前由 I 核对。

### 2.11 兼容、启用与迁移

“只增加字段”**不能**推出所有行为都向后兼容。成环拒绝、完整登记强制、字段模式下的新鲜度都会改变现有调用的结果。采纳的启用方式如下：

- 完整登记只对显式设置了能力项的类型生效，按类型逐个启用，并附③④的迁移说明。
- 拒绝成环和拒绝核心依赖插件在 P0b-3 合入时启用；仓库内目前只有测试调用方，PR 中需列出受影响的测试。
- 批末成环检查只检查经过本批新边的环，前提是已有的当前图本身无环。因此启用前必须先校验现有当前图：发现历史遗留的环时要显式报告并给出迁移方案，不能无声接受，也不能自动删边。这项校验只针对环；已有的过时（stale）依赖是正常状态，不得因此拒绝启用。新的持久化存储从空库开始，可在建库时直接启用；内存实现与现有测试的数据需在 P0b-3 PR 中单独说明并迁移（例如列出构造了环的测试用例）。
- 每一项启用在合并前由①负责人兼 I 核对，并在 PR 中写明启用方式和调用方需要做的改动；涉及③④的类型按类型通知并取得其实际输入，未通知时不得声称已通知。

## 3. 不在本提案范围内（列入后续接口队列）

- 多 cause 与跨 root：不能改变旧 `cause`、`root_feedback_id` 的含义，也不把“只合并同 root”当作已经决定。
- 完成记录：按所属模块分类型单写；“按行记录写入方”不是合法的替代方案。
- 请求 ID 与提交结果未知、远程 snapshot、可信身份与全部读取路径的授权：在 P1 之前另行设计。

## 4. 合并前核对清单

下列各项已按第 2 节采纳，**不再等待确认**。它们是 P0b 实现 PR 合并前由①负责人兼 I 核对的事项；核对结论由负责人在 PR 中给出，不由 AI 代为勾选，也不代填 `reviewed-by` / `reviewed-at`。

1. 2.1、2.2：`fields` 位于 `DependencyRecord` 顶层；写入路径上带 `fields` 的 `VersionRef` 被 `InvalidRequest` 拒绝（行为变化，PR 中写明）；旧调用语义不变。
2. 2.4：同版本重复输入合并（任一项是整个对象则按整个对象，否则取字段并集）；版本不同拒绝。
3. 2.5：字段模式的新鲜度（所选字段值相等即可登记较旧版本）；旧模式保持严格。这改变了字段模式下“依赖版本必须是当前版本”的语义，须在 PR 中写明。
4. 2.6：`canonical_json` 作为规范比较方法及共享测试向量；持久化后端的一致性在 P1 验证。
5. 2.8、2.9：空集登记可读；能力项缺省 false；核心/插件来源由可信注册来源决定。候选类型（`attribution`、`artifact`、`rule_selection`）按类型启用前，③④负责人须提供实际输入并被通知，通知与否以 PR 中的实际记录为准。
6. 2.10、2.11：批末检查与错误语义；`dependency_cycle` 的旧客户端兼容测试结果；启用前对现有当前图的环校验与迁移说明，以及受影响的测试清单。
