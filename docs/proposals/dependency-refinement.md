## 0. 摘要

| # | 决定 | 一句话 |
|---|---|---|
| D1 | 字段级依赖 | 依赖可以细到「对象的某个顶层字段」，例如「人物乙的 `name`」 |
| D2 | 名字不再特殊 | 名字和其他字段一样，推断结果可以依赖它；改名会让依赖名字的结果重新判断 |
| D3 | 正文用纯 Markdown | md 产物、活动名称和描述直接写名字，不再用 `[[person:<id>]]`、`[[place:<id>]]` |
| D4 | 各步骤能看到什么 | 划分活动看不到人物和地点；选规则、提取能看到；选规则的结果存下来并登记依赖 |
| D5 | 重新判断用最新规则 | 重新判断时，选规则和提取都用规则的当前版本；规则版本变化记为一个起因 |

## 1. 动机

1. **改名造成假的过时。** 人物的名字和参考存在同一个对象里，依赖按「对象 + 版本」判断是否过时。③归属模块的归属关系如果登记了对候选人物的依赖，改名产生的新版本会让它被查成过时，白白重新判断一轮。
2. **由名字推断出的内容不会更新。** 引用标记只保证显示的名字是最新的。正文里由名字推断出的内容（例如根据「王老师」写下「作为导师布置任务」）在改名后不会更新，因为 md 产物不依赖人物。
3. **选规则的结果没有依赖。** 规则可以带条件，例如「有某位老师参加的组会」。纠正或改名后，某条规则对某个活动可能变得适用或不再适用。但「没选中」不产生任何数据，也就无处登记依赖，系统查不出来。
4. **引用标记不是通用 Markdown。** 产物离开 ⑥客户端与 API 后（导出、给其他 Agent 读）都要先做替换。

## 2. 方案

### 2.1 D1：字段级依赖

- 依赖登记增加可选字段 `fields`：被依赖方 `payload` 的**顶层**字段名数组。不填表示依赖整个对象，与现在的行为相同。契约只增加字段，符合「只能增加，不能删除或改义」。
- ①存储与事件判断是否过时：

  | 登记 | 判为过时的条件 |
  |---|---|
  | 不填 `fields` | 登记的版本不是当前版本（与现在相同） |
  | 填了 `fields` | 登记的版本和当前版本相比，其中任一字段的值不同（规范化 JSON 比较） |
  | 任意 | 被依赖方已被整体替代 |

- 登记时仍要求被依赖方是当前版本，否则冲突 `stale_dependency`（不变）。
- 字段改了又改回去（A → B → A）不算过时：输入相同，结果应当相同。
- ⑤依赖分析模块生成修改描述时可以具体到字段，例如「乙.name：王老师 → 王同学」。
- MVP 只做顶层字段，数组内部（例如 `references` 里是否含某条声纹）不再细分。

### 2.2 登记规则：输入即依赖

**放进大模型输入（或确定性算法输入）的字段，就是要登记的依赖。** 由调用方的代码在构造输入时机械地记录，不让大模型自己报告用了什么。

- 原因：漏登记不会报错，那个字段改了以后这条结果永远查不出来；多登记只是多一次重新判断，结果不变时 ① 不写入、不发事件。
- 原始数据只追加、不修改，可以不登记。

| 依赖方 | 被依赖方 | `fields` |
|---|---|---|
| 归属关系（③归属模块） | 候选人物、地点 | `["references"]` |
| 选规则结果（④活动提取模块，见 D4） | 所属活动、候选规则 | 不填（整个对象） |
| | 活动时间内的归属关系 | 不填 |
| | 输入中出现的人物、地点 | 放进输入的字段，例如 `["name"]` |
| md 产物（④活动提取模块） | 所属活动、所用规则 | 不填 |
| | 活动时间内的全部归属关系 | 不填（沿用设计 7.2 的粗粒度） |
| | 输入中出现的人物、地点 | 放进输入的字段，例如 `["name"]` |

### 2.3 D2：名字不再特殊

- 改名和其他字段的修改一样：产生新版本，不带 `skip_history`。补充章节 3.4 的表里，改名本来就属于「其他所有写入」，表不用改。
- ⑤依赖分析模块查出依赖 `name` 的选规则结果和 md 产物，请求重新判断。修改描述带上新旧名字。
- 归属关系只依赖 `references`，所以改名**不会**引起重新归属（D1 保证）。
- 第一次命名（`name` 从 `null` 变成有值）同样会触发。

### 2.4 D3：正文用纯 Markdown

- md 产物的正文是标准 Markdown，人物和地点直接写名字；活动的名称和描述也一样。
- ⑥客户端与 API 直接渲染，不再做替换。外部动作建议的标题和备注本来就是纯文本，与此一致。
- 未命名人物：给大模型时用显示名 `#N`，正文里也写 `#N`。命名后，依赖它的产物会重新生成。
- 「什么影响了这条产物」只由依赖登记表达，正文里不再有 id。
- 代价：
  - 改名后，依赖这个名字的产物都会生成新版本（正文里的名字一定变）。
  - 这些产物上还没审核的外部动作建议会作废并重新生成。这是对的：旧建议里写的也是旧名字。
  - 给未命名人物起名很常见，大模型调用会增多。
  - ⑥客户端与 API 不能把正文里的人名做成跳转链接（MVP 验收没有这一项）；⑧检索索引模块【以后】按人物检索、过滤需要另想办法（设计 10.2）。

### 2.5 D4：各步骤能看到什么

| ④活动提取模块的步骤 | 能否看到人物、地点 | 依赖 |
|---|---|---|
| 划分活动 | 不能，只用原始数据 | 不登记。「活动不依赖归属关系」保持不变 |
| 选规则 | 能 | 结果存为「选规则结果」，登记依赖 |
| 提取 md 产物 | 能 | 见 2.2 |

- 活动的名称和描述由划分活动这一步生成，所以不能写来自语义信息的人名和地名。转写里说出来的名字属于原始数据，不受限制。
- 新增数据类型**选规则结果** `rule_selection`：语义信息，由④活动提取模块负责写，每个活动一个。payload 记下当时的候选规则版本和选中了哪些规则。
- ⑤依赖分析模块的分发登记表增加：选规则结果 → ④活动提取模块。
- ④活动提取模块重新判断选规则结果后：
  - 新变得适用的规则：生成新的 md 产物（和建议）；
  - 不再适用的规则：对应产物整体替代，产物上还没审核的建议一并作废；
  - 仍然适用的规则：不动，由产物自己的重新判断处理。
- **待定：md 产物是否登记依赖选规则结果**，由④活动提取模块的负责人决定（见第 5 节第 3 条）。

### 2.6 D5：重新判断用最新规则

- 规则的新增、修改、删除**仍然不主动触发**重新判断（⑤依赖分析模块忽略规则修改，补充章节 4.3 不变）。「新规则不作用于历史」只是为了避免一改规则就重算全部历史，不是原则问题。
- 某个活动因为其他修改被重新判断时：
  - 选规则：按当前的全部规则重新选，包括之后新增的，不包括已删除的。
  - 重新提取 md 产物：用规则的当前版本；规则已删除时，产物整体替代，还没审核的建议作废。
- **规则版本的变化是一个额外起因。** 它只有④活动提取模块在重新判断时才发现，⑤依赖分析模块不知道。建议 ③归属模块、④活动提取模块每处理完一次「请求重新判断」，就写一条系统记录（暂称「重新判断结果」），写明：对应的请求 id、结果有没有变化、额外起因（例如「规则 R：v3 → v5」）。⑤依赖分析模块写传播记录时读取它。
- 这条系统记录同时补上一个已知空缺：重新判断结果不变时，⑤依赖分析模块收不到任何信号（设计 8.1 第 5 步）。
- 设计 7.7 的验收加前提：**规则版本没有变化时**，没受影响的 md 产物重新判断后与旧版本逐字相同。

## 3. 传播仍然会停

依赖关系（箭头读作「被……依赖」）：

```
人物、地点的 references ──► 归属关系 ──┬──► 选规则结果
人物、地点的 name 等字段 ───────────────┼──► md 产物
活动、规则 ────────────────────────────┘
```

- 没有任何数据依赖选规则结果和 md 产物；外部动作建议不参与依赖分析。
- 人物、地点的字段只由用户修改；③归属模块重新判断归属关系时不改参考。
- 活动不依赖归属关系和人物、地点（D4）。
- 图中没有环。设计 8.2 的理由仍然成立，只需把「md 产物」扩展为「md 产物和选规则结果」。

【以后】让各步骤都能看到人物和地点并登记依赖，允许依赖成环，另设机制防止无限循环（对应设计 8.4 的【以后】）。

## 5. 待决定的问题

1. **未命名人物的写法**：正文里写 `#N`，但 `#N` 的编号规则在设计里没有定义。
2. **「重新判断结果」由谁写**：登记表里一个数据类型只有一个负责写的模块，而 ③归属模块、④活动提取模块都要写。可以分成两个类型，也可以允许多个负责模块（要改 `data-types` 契约）。
3. **md 产物是否依赖选规则结果**（待定，由④活动提取模块的负责人决定）：
   - 不依赖：选规则结果变化后，由④活动提取模块在同一批写入里新增或整体替代产物，和「产物更新后作废旧建议」一样在模块内部完成（补充章节第 5 节）。产物的内容只由它自己的依赖触发重新判断。
   - 依赖：选规则结果的任何变化都会让已有产物被查成过时，多一轮深度更大的重新判断；新增的产物仍然需要④活动提取模块自己生成。
4. **产品行为**：D5 让一次纠正可能使新规则作用到历史活动上，生成新的产物和建议。这和设计 0.3「会影响历史结果的操作，一律由用户主动发起」的本意是否一致？界面上是否需要提示？
5. **并发**：同一个活动的选规则结果和 md 产物可能同时收到「请求重新判断」。依靠 ① 的冲突检测重新读取、重新计算（`write_with_retry`），需要在④活动提取模块的实现中测试。
6. **选规则时放进哪些字段**：按「输入即依赖」，取决于④活动提取模块负责人设计的提示词。
