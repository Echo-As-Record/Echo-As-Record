# 提案：把“合并人物”提前进 MVP

> **状态：proposed，未采纳。** [设计 v1.2](../design/design-v1.2.md) 第 6.4 节把“合并人物”列为【以后】，规定 MVP 中人物拆成多个对象时“先通过参考和重新判断补救”。本文提议把合并人物提前进 MVP，改变已采纳的范围，需要负责人明确决定。涉及反馈格式的契约增补，采纳后仍需①负责人与 I 审核。

## 1. 问题：同一个人会被拆成很多未命名人物

按第 6.1 节，声纹匹配不上已有对象时，③新建一个未命名人物，并把这段声纹设为它的第一个参考。于是同一个人的声音只要有一次没匹配上（换了麦克风位置、骑车有风、说话音量不同），就会多出一个“分身”。之后同类场景下的声音会和这个分身最像，分身越积越多。

旧 Ear 的实测说明这不是假设：

- 旧 Ear 同样会为认不出的声音建匿名音色，积累了约两千个没有主人的音色。
- 修好版本号问题、用原音重算全部模板后，用户本人 5 段留出录音里，本人与第一个竞争者的分差只有 0.01–0.04，低于要求的 0.08。抢第一的正是用户自己那些匿名音色。

PR #16 中③的匹配实现是“所有参考里相似度最高且过阈值者胜出”，不比分差。结果是本人的新声音大量归到某个分身上，而不是归到用户本人。

## 2. 现有补救为什么不够

设计里现成的手段：

1. **逐条纠正**：一次把一段声纹从分身移到本人。分身有几十个、每个下面有几十段声音时，工作量不可接受。
2. **参考管理 + 重新判断**：把分身的参考全部移到本人名下，分身因此没有参考、不再参加匹配；名下还有声纹时显示“#N 还有 M 段声音，可能也是 X”，用户点重判。问题有三个：
   - 每个分身都要走两步，分身多时同样繁琐；
   - 重判时这些声音会和**其他分身**比较，未必落到本人名下；
   - 用户确认或纠正过、归在分身名下的声音受保护，重判不会动它们，分身因此永远留着，无法整体替代。

## 3. 做法：一次合并

新增③的反馈命令 `merge_persons`（暂拟名）：把一个或多个来源人物 S 合并进目标人物 T。用户在⑥里选中几个人物，指定保留哪一个。

③处理时在同一批写入里完成：

1. **参考**：S 的全部参考移到 T。一条原始数据仍最多是一个对象的参考。
2. **归属**：当前指向 S 的归属全部改指向 T，**直接改，不重新匹配**，因为用户已经说明 S 和 T 是同一个人。
3. **用户确认保护**：原本受保护的归属改指向 T 后**仍受保护**。合并本身是用户的明确判断，不属于第 6.2 节禁止的“自动重新归属”。
4. **来源人物**：S 整体替代，记下合并去向（例如 `merged_into = T`），⑥据此把对 S 的链接引到 T。
5. **名字**：T 保留自己的名字；T 未命名而某个 S 已命名时，由用户在合并时选定名字。名字变化按现有规则触发依赖 `name` 的下游。
6. **传播**：归属变化按现有依赖分析传给下游。合并会一次改很多条归属，受⑤现有的规模和轮次限额约束，超限时记录并提示。

合并不提供撤销。合错时用户按现有方式逐条纠正，或把参考移回一个新建人物。

## 4. 范围

- **只合并人物**。地点在 MVP 中只能由用户手动创建，不会自动产生分身，不需要合并。
- **不做自动合并建议**。设计里“自动建议合并”“重判结果与用户判断不同时提示”仍为【以后】。
- **不改匹配算法**。是否在匹配中加入分差门槛、阈值取多少，仍由③负责人决定。分差门槛能减少“错归给分身”，但不能消除分身，两者不互相替代。

## 5. 待决

1. 是否把合并人物提前进 MVP（本文的核心决定）。
2. 第 3 条：合并时保护状态随归属转移，是否接受。
3. 第 4 条：来源人物用整体替代加 `merged_into` 表示，还是另设字段；⑥如何展示被合并的人物。
4. 一次合并的来源人物数量上限。

## 6. 影响与验收

- **③**：新增 `merge_persons` 反馈处理。
- **⑥**：选择多个人物并指定保留目标的入口；被合并人物的跳转。
- **⑤**：无新接口；一次合并会产生大量归属变化，需验证在限额内能完成传播。
- **①、契约**：反馈 payload 与人物 `merged_into` 字段的契约增补，①负责人与 I 审核。

验收用合成数据：

1. 合并后 S 的参考全部在 T 名下，没有一条参考同时属于两个对象。
2. 原先指向 S 的归属全部指向 T；受保护的仍受保护。
3. S 被整体替代，按 id 仍可读取，并能查到合并去向。
4. 之后到来、与原 S 参考相似的声音归到 T。
5. 依赖这些归属或 T 名字的下游被重判；重复提交同一合并反馈不产生重复版本或重复重判。
6. 用合成的“一人多分身”数据对比：合并前本人召回率，与合并后的召回率。
